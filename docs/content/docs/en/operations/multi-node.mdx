3x-ui can manage **multiple servers** from a single master panel, and override
how each inbound is advertised in subscriptions with **managed hosts**.

## Nodes

A **node** is another 3x-ui panel that your master panel manages over the node's
API. The master polls each node and shows its status, versions, CPU/memory,
uptime, and traffic in one place.

### Add a node

Provide the node's connection details:

| Field             | Notes                                                                 |
| ----------------- | --------------------------------------------------------------------- |
| **Name**          | Unique label (e.g. `de-fra-1`).                                        |
| **Scheme**        | `https` (default) or `http`.                                          |
| **Address / Port**| The node panel's host and port.                                       |
| **Base path**     | The node's web base path.                                             |
| **API token**     | A Bearer token created on the node (not needed in mTLS mode).         |
| **TLS verify**    | `verify` (default), `skip`, `pin` (pin a cert SHA-256), or `mtls`.    |
| **Inbound sync**  | `all` inbounds, or `selected` by tag.                                 |
| **Outbound tag**  | Optionally reach the node **through** a named outbound (egress bridge).|

The master verifies reachability when you add or test a node. It then sends a
**heartbeat** every few seconds, updating the node's status (`online` / `offline`)
and emitting `node.up` / `node.down` events (see the
[Telegram bot](/docs/operations/telegram-bot) and [Discord bot](/docs/operations/discord-bot)).

<Callout type="info">
  Nodes are identified by a stable per-panel GUID, so a node keeps its identity
  across restarts. A node can itself manage further nodes — the master surfaces
  those as read-only **transitive** sub-nodes (Node 1 → Node 2 → Node 3).
</Callout>

### Install a node with one command

**Nodes → Install command** generates a command to run as root on a fresh server:

```bash
curl -fsSL https://panel.example.com:2053/abc/install-node.sh | bash -s -- \
  --panel https://panel.example.com:2053/abc --token '…' --name de-fra-1
```

The master serves `install-node.sh` itself, with its own version baked in as the
default release the node installs. The script runs the normal non-interactive
installer, reads the result it writes (`/etc/eternal/install-result.env`: panel
address, base path and API token), and posts them with the token to
`{basePath}/join/node` on the master. The master checks that it can reach the new
panel and then adds it as an enabled node that syncs all inbounds, so it appears in
the node list within a minute.

The token is single-use, valid for one hour, and stored on the master only as a
hash. A join that fails (for example the master cannot reach the new panel yet)
keeps the token, and the script retries for about a minute. The endpoint takes
no session, is rate limited per client IP, and refuses private or loopback node
addresses, `mtls` and outbound bridges: set those on the node afterwards.

Options go after the token:

| Option | Effect |
| --- | --- |
| `--name NAME` | the node's name (default: the server's hostname) |
| `--port PORT` | the node panel's port (default: random) |
| `--version TAG` | the Eternal release to install (default: the master's version; the latest release if that one is not published) |
| `--installer-url URL` | use this `install.sh` instead of the one on GitHub |
| `--node-tls verify\|skip\|pin` | how the master verifies the node's certificate (default `verify`) |
| `--insecure` | do not check the master's TLS certificate |
| `--pin sha256//KEY` | accept only the master's TLS key (the panel adds it when its certificate is self-signed) |
| `--detect` | print what is on the server and change nothing |
| `--uninstall --yes` | remove Eternal, its database and Xray from the server |

A server that already runs Eternal is not reinstalled: the script only registers it,
using the result file of the earlier install.

<Callout type="info">
  The installer and the release archives are downloaded from GitHub
  (`rad1in/eternal`). On a server that cannot reach GitHub, host `install.sh`
  yourself and pass `--installer-url`, or add the node by hand.
</Callout>

### Mutual TLS (mTLS) between master and node

For the strongest trust, use `tlsVerifyMode = mtls` (requires `https`):

<Steps>

<Step>
### Get the master's CA

On the master, fetch its node-auth CA certificate (the CA private key never
leaves the panel).
</Step>

<Step>
### Trust it on the node

Paste that CA into the node's "trusted CA" setting. It takes effect on the node's
next restart.
</Step>

<Step>
### Switch the node to mTLS

Set the node's TLS verify mode to `mtls`. The master now presents a client
certificate instead of an API token.
</Step>

</Steps>

### Metered nodes: traffic cap and cost

For a VPS with a monthly transfer allowance, set **Monthly traffic cap** (GB),
the **billing day** on which the provider's counter resets, and what happens at
the cap in the node's edit dialog:

- **Send an alert only** publishes a `node.cap_reached` event to Telegram,
  Discord, email and webhooks (enable it in the notification event lists).
- **Alert and disable the node's inbounds** also disables every enabled inbound
  on that node. When the next billing period starts, or you raise the cap, only
  the inbounds the cap itself stopped are enabled again; inbounds you disabled
  by hand stay off.

The panel counts the traffic it accounts on the node's inbounds, checked once a
minute. That excludes anything else the VPS sends (SSH, package updates, other
services), so it runs below the provider's meter — set the cap a little under the
real allowance. A node's first sample only sets a baseline, so history from before
the cap was configured is not counted.

**Monthly cost** and currency are shown per node on the Nodes page, with the
cost per terabyte used so far this period (withheld until 10 GB have flowed) and
the total cost per currency. The panel does not know what your clients pay, so
it shows costs and traffic only and calculates no profit.

### Failover to a backup node

A node's **Failover** section names a **backup node** and a delay (default 120 s).
While the node has been offline longer than the delay, the subscription links of
its inbounds (raw, JSON and Clash, and VPN profiles) advertise the backup node's
address instead. The moment the node is back online its own address returns.

Failover only moves an address, so the backup has to be ready to serve the same
clients: a link is moved only for an inbound that the backup also has, enabled,
with the same protocol and port (create it with **Clone** to another node, keeping
the same keys and clients). The backup must be enabled and online. Inbounds with a
custom share address, and managed hosts with their own address, keep it. Clients
already connected are not moved; they pick the new address when they refresh their
subscription, so a short subscription update interval makes failover faster.

### Speed test

The dashboard icon on a node row runs an on-demand test of the path between the
master and that node: five latency pings (min / avg / max, jitter, lost pings),
then an 8 MiB download and a 4 MiB upload over the same authenticated API the
panel syncs through. Nothing is stored. A node running an older panel still
reports latency; its throughput is shown as unavailable until you update it.
The test moves about 12 MiB, so avoid running it repeatedly on metered links.

## Managed hosts

A **managed host** is an override endpoint attached to an inbound. At
subscription time, each enabled host renders an additional share link / proxy
with its own address, port, TLS, SNI, host header, path, and more — superseding
the older "external proxy" list. Use them to:

- front an inbound through a **CDN** (Cloudflare) with a different address/SNI,
- advertise **multiple domains** or per-region endpoints for one inbound,
- tweak ALPN, fingerprint, ECH, or mux per endpoint.

Each host has a remark (which supports the same
[template variables](/docs/config/share-links#remark-template-variables)), an
enable toggle, a sort order, and can be **excluded from specific subscription
formats** or **scoped to specific nodes**.

<Callout type="info">
  Hosts whose address/port point at a CDN let you keep the real server address
  private while clients connect through the CDN edge.
</Callout>

### Clean IP scanner

**Hosts → Clean IP scan** probes a list of CDN addresses from the panel host and
ranks them by packet loss and latency. Enter IPs, CIDR ranges or `a.b.c.d-e.f.g.h`
ranges; a range larger than 2048 addresses is sampled at random. Give an SNI to
make each attempt a TLS handshake whose certificate must match that name, so an
address that is reachable but hijacked is reported as a certificate mismatch.
Without an SNI only the TCP connection is tested.

A reachable address can be applied to an existing host (replacing or extending
its addresses) or added as a new host on an inbound. Loopback, private and
link-local addresses are never probed. The scan runs on the panel host, which is
usually outside the network that filters your clients: an address that is clean
there may still be blocked for them, so treat the result as a shortlist and
verify the chosen address from a client.
